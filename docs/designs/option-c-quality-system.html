Option C · full quality system

A report that shows its evidence and marks what it cannot verify.

Option C separates the evidence from the writing. Each persona records claims with quotations, code groups and counts those claims, and the writer receives a plan rather than the raw transcripts. The report can still be specific. Every unverified field is marked, and QA allows at most one per run.

Chosen by the user

This page explains Option C. It is not an implementation record. The first slice is S1: the claim ledger and the derived report.

Problem

One call both decides what the evidence says and writes the report.

Today, SynthesizeArtifactResultsUseCase sends the raw monologues to one model. That model writes the overview, the findings, the counts, the citations, and the answer in one pass. When the model writes "all three", no code checks that it counted three personas.

The same pass can move a persona onto the wrong objection, omit a persona from a split, or invent a price. The report is specific, but its specificity is not tied to the record.

What the reader sees

"All three personas hit the same wall: routing rules ... behind the Growth tier."

One persona was blocked at action because the brief offered no beta sign-up. The persona was not blocked by price. The prose moved that persona onto the price wall.

The same run

"A disagreement split of 1 and 1 against a cohort of 3."

The third persona is absent. A reader cannot tell whether that persona had no view, held a third view, or was overlooked.

Why the score is stuck

Specificity is already high. Grounding and differentiation are the floor. Actionability follows the answer, so it rises only when the answer is true.

A stronger prompt can lower the error rate. It cannot make a count true, because the model that writes the sentence also chooses the number.

Terms

Six words have fixed meanings.

The design uses ordinary words with private meanings. The page uses one meaning for each word, the same meaning as the design file.

Claim

One assertion and one quotation.

A claim belongs to one persona. The quotation must be a complete sentence from that persona's monologue.

Support gate

Does the quotation support the claim?

A model answers support, partial, or unsupported. Only support claims enter the cohort ledger.

Group

Claims on the same topic.

Code counts distinct personas for, against, and neutral. A group with enough personas becomes a finding.

Verdict

One choice from four.

Adopt, trial, reject, or undecided. The set is fixed for every role and artifact.

Frame

The task for one persona.

It holds the role, the task, the entry point, and the decision question for this artifact.

Plan

The writer's only input.

It holds verified claims, code counts, citations, and facts. It holds no raw monologue.

The important seam is between the ledger and the writer. The writer receives a SynthesisPlan. It never receives rawAnalysis. That one type boundary is what stops the prose from inventing a count or a quote.

Data flow

The pipeline has six stages and three parallel groups.

The profile runs once before the personas because the content kind chooses the decision question. Each persona then runs a monologue, an extraction, and a claim pass. Extraction and claims read the same monologue in parallel. After all personas settle, support and clustering run in parallel, and the writer runs last.

Critical

Parallel work

Inside one persona, the extraction and claim pass both read the monologue, so they run side by side. After all personas, the support gate and clustering both read the claim set, so they also run side by side.

This keeps the added wall time below the added call count. The profile call is the one serial addition before the personas start.

What code owns

It checks each quotation against the monologue. It keeps only supported claims. It counts distinct persona ids, builds citations, and adds a No clear view bucket when a split does not cover the cohort.

What the model owns

It reads a claim and its quotation and returns a support level. It groups claims by topic. It writes the finding wording. It never sets a count or a quotation in the final report.

Roles and verdicts

A role changes where the persona starts.

The role changes which parts of the artifact the persona examines and the order it examines them. The role does not choose the verdict. Every persona chooses from the same four verdicts, so the report can compare the cohort.

Facts and content kinds

Facts come from the artifact, not from the writer.

The profile extracts exact facts and the content kind before the personas start. The writer receives those facts in the plan. The validator then checks currency amounts and percentages against the fact sheet.

The content kind also decides the stage anchor. A landing page has none. A feature brief uses a heading or a quote. A video script uses a timestamp, so the drop-off point is a real position in the script.

Landing page

No stage anchor.

The persona reads a screen. The journey describes what it thought at each stage, not where the thought appeared in a document.

Feature brief

Heading or quote anchor.

The profile decides whether the text has headings. A heading or a verbatim quote must match the artifact text.

Video script

Timestamp anchor.

Each reached stage needs a timestamp, and the timestamps must rise. The terminal timestamp is the point where attention broke.

Options

Why C, and not A or B.

A adds a verifier to the current free-prose report. B derives counts from a claim set. C adds the role frames, fixed verdicts, the fact sheet, and the content-kind anchors.

Option A

Semantic verifier only

One support call checks each finding's quotation. Unsupported findings are dropped. The prose still writes its own counts and splits.

Off: all three claims survive.

Still fails: a verifier can drop one quote and leave "all three" intact.

Option B

Derived aggregates

A claim set replaces free-prose counts. Code owns counts, citations, and splits. One support call checks the claims.

On: 2 of 3 claims survive.

Still fails: personas share one reasoning spine, and the report has no fact sheet or video anchor.

Option C · chosen

Full quality system

B plus role frames, fixed verdicts, an artifact fact sheet, and content kinds with stage anchors. The writer reads the plan and never the transcripts.

Fixes: grounding, split arithmetic, differentiation, and video schema fit.

S1 contract

  • A claim without a verbatim quotation cannot enter the ledger.
  • Only a supported claim can set a count.
  • The split sums to the completed count with `No clear view`.
  • The writer sees the plan, never the transcript.
  • A failed validation marks the field and stores the warning.
  • QA allows at most one marked field per run.

S1 includes

A narrow warning banner, inline marks on fields that already render, and a PDF warning stamp. It does not change personas, intake, the full report design, auth, or the VPS setup.

Quality harness

scripts/quality-floor.ts runs the real pipeline ten times. Each run is reviewed by ten fresh contexts across six roles. The script records the median for specificity, grounding, differentiation, and actionability.

The floor is 8.0. A green structural report with a 5/10 blind score fails. A 9/10 blind score with a broken citation also fails. The structural gate also fails a run with more than one marked field; a missing claim set counts as one.

Limits

What C does not fix.

Five personas are not a representative sample. The support gate is not a proof. The blind harness is the only evidence for the floor. If the artifact does not state a fact, the report must say so.

Five personas are not a population.sample

The report describes a cohort. It does not claim a market. The counts say "of 5", not "of the market".

The support gate can still accept a plausible wrong claim.support

The gate removes unsupported claims and prevents them from setting counts. The blind review catches the cases the gate misses.

A green unit suite is not a quality score.proof

Structure tests prove the shapes. They do not prove the report is useful. S4 runs the real pipeline and the blind reviewers.

A screenshot fact is harder to check than a text fact.facts

Code can check a quotation against text. It cannot check a quotation against a screenshot. Those facts are marked, and the guard is numeric for screenshots.
